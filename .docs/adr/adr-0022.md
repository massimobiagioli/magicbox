# ADR-0022: Dkron for scheduled jobs between services

- **Date:** 2026-11-04
- **Deciders:** MagicBox maintainers

## Status

Accepted

## Context

Apps on MagicBox need scheduled work (nightly clean-ups, periodic syncs,
reminders). Cron inside each app container duplicates schedules, has no
history and no UI, and runs twice when an app is scaled. A central scheduler
that calls the apps' endpoints keeps the schedules in one place.

Dkron (LGPL-3.0, Go, single binary) is a cron service with a web UI, a REST
API, job history, retries, dependent jobs, and executors for HTTP, shell,
gRPC, RabbitMQ, Kafka and NATS. Its open-source edition has no
authentication (ACLs are in Dkron Pro). Verified on `dkron/dkron:4.2.1`: the
UI loads its assets and the API through relative paths (`./assets`,
`../v1`) and uses a hash router, so it works under a gateway prefix; only
`/` answers with a redirect to the absolute path `/ui/`.

## Decision

- Dkron is the Portainer stack `dkron`, deployed by `make deploy`, image
  pinned (`stacks_dkron_image`), one server node (`--bootstrap-expect=1`),
  data in the volume `dkron_data`.
- Host networking with every listener on `127.0.0.1` (HTTP
  `stacks_dkron_port` 8090, Serf 8946, RPC 6868): nothing is reachable from
  the LAN directly, and HTTP jobs reach the apps on `127.0.0.1:<port>` (apps
  registry) or through the gateway.
- Kong serves the UI and API at `https://magicbox.local/dkron/` (prefix
  stripped) with the `basic-auth` plugin: user `stacks_dkron_user` (`admin`),
  password `vault_dkron_password`; credentials are not forwarded. `/dkron`
  and `/dkron/` redirect to `/dkron/ui/`.
- Apps manage their own jobs through the API
  (`https://magicbox.local/dkron/v1/jobs`, same login), or jobs are created
  in the UI.

## Alternatives

- **Cron in each app container:** no central view or history; duplicate runs
  with more than one replica; rejected.
- **Jenkins scheduled jobs:** already present, but meant for builds; its
  agent has the Docker socket (root-equivalent), too much power for app
  schedules; rejected.
- **Ofelia (Docker label cron):** light, but no UI and only `docker exec`/
  `docker run` jobs; rejected.
- **Exposing Dkron on its own LAN port:** no login at all; rejected.

## Consequences

- Anyone with the Dkron login can run shell commands as root inside the
  Dkron container, which shares the host network: treat it as an admin
  credential.
- Calls from Dkron to apps go over the loopback; apps must still check what
  they accept (Dkron adds no authentication to its HTTP calls unless the job
  sets headers).
- Single node: no high availability; jobs and history live in `dkron_data`
  (back it up, or recreate jobs from the apps).
