# ADR-0001: Ansible from a uv-managed .venv as the only provisioning path

- **Date:** 2026-10-28
- **Deciders:** MagicBox maintainers

## Status

Accepted

## Context

MagicBox is a single GMKtec Intel Mini PC that must be rebuilt reproducibly and
changed without manual drift. The operator's workstation (the Ansible
controller) may run macOS or Linux with any system Python. Tool versions that
float between runs (ansible-core, collections, linters) cause non-reproducible
results.

## Decision

- All host configuration is applied by `playbooks/site.yml` and the roles under
  `roles/`. Manual changes on MagicBox are limited to the bootstrap checklist in
  the installation manual (OS install, admin user, SSH key).
- Controller tooling is installed into a project-local `.venv` by `uv`.
  `pyproject.toml` pins direct dependencies exactly; `uv.lock` pins the full
  tree; `.python-version` selects Python 3.14.
- Ansible collections are pinned exactly in `requirements.yml` and installed
  into `.ansible/collections` (project-local, git-ignored).
- Every helper script lives in `tools/` and is run with `uv run`.

## Alternatives

- **System/Homebrew Ansible:** version depends on the workstation; rejected.
- **pip + requirements.txt:** works, but no lock of transitive dependencies
  without extra tooling and slower environment creation; rejected.
- **Shell scripts on the host:** not idempotent by default, hard to review;
  rejected.
- **NixOS / cloud-init only:** stronger reproducibility, but higher learning
  cost and not aligned with the requested stack; rejected.

## Consequences

- `make setup` produces an identical controller environment on any machine
  with `uv`.
- Upgrading ansible-core or a collection is an explicit change to
  `pyproject.toml`/`uv.lock`/`requirements.yml` and must pass `make check`
  and `make test-container`.
- The controller needs network access to PyPI and Ansible Galaxy for setup.
