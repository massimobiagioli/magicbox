# ADR-0017: App jobs and ports from a git-ignored apps registry

- **Date:** 2026-10-29
- **Deciders:** MagicBox maintainers

## Status

Accepted (amends ADR-0016)

## Context

With ADR-0016 a new app still needed manual work in several places: an entry
in the tracked `apps/registry.yml`, a Multibranch Pipeline created in the
Jenkins UI, the app name and host port repeated in the app's `Jenkinsfile`
and `deploy/stack.yml`, and CI files copied from another app. The owner wants
the apps listed in a YAML file outside git and as few manual steps as
possible: `make apps` must also create the Jenkins jobs.

## Decision

- **Registry:** `inventory/group_vars/magicbox/apps.yml` (`magicbox_apps`),
  git-ignored like `inventory/hosts.yml`, loaded by Ansible for every
  playbook; template `inventory/apps.example.yml`. Each entry: `name`,
  `port`, `repo` (GitHub HTTPS URL). `apps/registry.yml` is removed.
- **Jenkins jobs:** plugin `job-dsl` (pinned in `stacks_jenkins_plugins`).
  `CASC_JENKINS_CONFIG` is the directory `/etc/jenkins/casc`: `jenkins.yaml`
  (`make ci-cd`) plus `apps.yaml` (`make apps`), a JCasC `jobs:` section with
  one `multibranchPipelineJob` per app: GitHub source with credential
  `github`, all branches, no pull requests, scan every
  `stacks_jenkins_scan_interval`. `make apps` applies it with a JCasC reload
  (no restart, running builds continue) and starts the first scan of new jobs.
- **Ports for the pipelines:** `make apps` writes `/opt/magicbox/apps/apps.json`
  (name -> port). The deploy step mounts it read-only and passes `APP_NAME`,
  `APP_PORT` and `IMAGE_TAG` to the Portainer stack.
- **Generic CI files in the template:** `Jenkinsfile` takes the app name
  from the job name; `deploy/stack.yml` uses `${APP_NAME}` and `${APP_PORT}`;
  the Dockerfile has the `ci` stage. Nothing app-specific is left to edit.
- **`tools/new_app.py`:** copies the template, renames the project, makes the
  first commit, appends the app to the registry with the first free port and
  `https://github.com/<stacks_jenkins_github_user>/<name>`, and with
  `--create-repo` creates the private GitHub repository and pushes (`gh`).

## Alternatives

- **Jobs through the Jenkins REST API (`config.xml`):** no extra plugin, but
  XML tied to plugin internals and harder to keep idempotent.
- **GitHub Organization Folder:** discovers repositories automatically, but
  needs a GitHub organization or a user scan of every repository, and the
  Kong route and port would still need the registry.
- **Restarting Jenkins after a registry change:** simpler than the reload,
  but interrupts running builds.
- **Registry tracked in git:** rejected by the owner (local, per-installation
  data, like the inventory).

## Consequences

- New app: `uv run tools/new_app.py <name> --create-repo` then `make apps`.
  The GitHub token of Jenkins must be able to read the repository (simplest:
  token with access to all repositories).
- Removing an app from the registry removes its Kong route and its port from
  `apps.json`, not its Jenkins job or Portainer stack: delete them by hand.
- Job settings are owned by Ansible: changes made in the UI are overwritten
  at the next Jenkins start or `make apps`.
- The registry is not in git: back it up with the inventory.
- `make ci-cd` must run once after this change (new plugin, JCasC directory).
