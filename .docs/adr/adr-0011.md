# ADR-0011: Default stacks deployed as Portainer stacks by a separate playbook

- **Date:** 2026-10-28
- **Deciders:** MagicBox maintainers

## Status

Accepted

## Context

The owner wants default services on MagicBox: RabbitMQ, PostgreSQL ("LTS"),
Ollama, and a Grafana-based observability stack. They should be visible and
manageable in Portainer, yet reproducible from this repository. PostgreSQL has
no LTS channel: every major version is supported for five years. On
2026-10-28, 18 is the newest major (18.6, supported until 2030-11-14); 19 is
not published on Docker Hub.

## Decision

- A separate playbook, `playbooks/stacks.yml`, runs the `stacks` role. It
  deploys each name in `stacks_enabled` as a **Portainer standalone stack**
  in the site environment (ADR-0010) through the Portainer API:
  - compose files are Jinja templates in `roles/stacks/templates/`;
  - secrets are passed as stack environment variables from the vault, never
    written into compose files;
  - configuration files mounted by containers live in
    `/opt/magicbox/stacks/<stack>/`; a checksum of them is passed as
    `MAGICBOX_CONFIG_REVISION` and used as a container label, so a config
    change recreates the affected containers;
  - a stack is created when missing and updated only when its compose file or
    environment differs, which keeps runs idempotent.
- Stacks and pinned images:
  - `rabbitmq` - `rabbitmq:4.3.7-management` (AMQP 5672, management UI 15672);
  - `postgresql` - `postgres:18.6` (5432), the newest major with the longest
    support window, used as the "LTS" choice;
  - `ollama` - `ollama/ollama:0.40.12` (11434), CPU inference;
  - `observability` - `grafana/grafana:13.2.5` (HTTPS 3000, using the MagicBox
    certificate), `grafana/loki:3.7.9` and `grafana/alloy:v1.21.2`
    (ADR-0013), both internal-only.
- All data is in named volumes (`rabbitmq_data`, `postgresql_data`,
  `ollama_data`, `loki_data`, `alloy_data`, `grafana_data`).
- The playbook never deletes stacks or volumes. Removing a name from
  `stacks_enabled` only stops managing it.
- Verification checks containers are running/healthy, PostgreSQL
  `pg_isready`, the RabbitMQ management API with the vault credentials, the
  Ollama API, Grafana over HTTPS with CA validation, and that Loki holds logs
  shipped by Alloy.

## Alternatives

- **`community.docker.docker_compose_v2` directly:** simpler, but the stacks
  would show up in Portainer as "limited" (externally managed); rejected.
- **Git-based Portainer stacks:** needs a reachable Git repository with
  credentials; rejected for now.
- **PostgreSQL 17 or 16:** older with a shorter support window; no reason to
  prefer them for a new install.

## Consequences

- Stack environment values, including passwords, are stored in Portainer's
  database. Portainer is already root-equivalent (ADR-0006).
- Service passwords apply only when the data volume is first initialised;
  rotating them means changing them in the service and in the vault.
- Plain-text protocols on the LAN: RabbitMQ (AMQP and management UI),
  PostgreSQL (SCRAM authentication, unencrypted data) and Ollama (**no
  authentication**). Access is LAN-only (ADR-0012). Adding TLS is future work.
- Edits made to these stacks in the Portainer UI are overwritten on the next
  `stacks.yml` run.
