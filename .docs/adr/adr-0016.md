# ADR-0016: Apps deployed by Jenkins and registered in the API gateway

- **Date:** 2026-10-29
- **Deciders:** MagicBox maintainers

## Status

Accepted

## Context

Applications (built from `templates/python-fastapi-app`) live in their own
GitHub repositories. A push to `main` must lint, test and deploy them on
MagicBox (Jenkins, ADR-0014), and each must be reachable at
`https://magicbox.local/<app>` through Kong (ADR-0015). Kong runs on the host
network and reaches upstreams on `127.0.0.1`. The Jenkins agent runs builds
against the host Docker engine, but sits on a Docker bridge network: ufw
admits Portainer (9443) only from `magicbox_lan_cidr`, so the agent cannot
call the Portainer API directly.

## Decision

- **Registry:** `apps/registry.yml` (`magicbox_apps`) lists each app: `name`
  (Portainer stack, container and URL path) and `port` (host port published
  on `127.0.0.1` only, range 18000-18999). `make apps` (`playbooks/apps.yml`)
  validates it, adds a Kong route `/<name>` -> `127.0.0.1:<port>` (prefix
  stripped) per app, redeploys Kong, checks the routes of deployed apps and
  reports apps not deployed yet. `playbooks/api-gateway.yml` loads the same
  registry, so a gateway redeploy keeps the app routes.
- **Pipeline (in each app repository):** `Jenkinsfile` on agent label
  `docker`. Every branch: build the Dockerfile `ci` stage, then **Lint**
  (ruff) and **Test** (pytest) inside it; `main` only: **Build**
  `magicbox/<name>:<commit>` on the host engine, **Deploy**, **Verify**
  (container healthy, runs the new image).
- **Deploy:** the pipeline runs `deploy/portainer_deploy.py` (standard
  library) in the `ci` image on the host network (`--network host`,
  `--add-host magicbox.local:127.0.0.1`, host CA mounted read-only). It
  creates or updates the Portainer stack `<name>` from `deploy/stack.yml` with
  `IMAGE_TAG`, using the Jenkins credential `portainer-api-token`. The stack
  uses `pull_policy: never`: images are built on MagicBox, no registry.

## Alternatives

- **Agent on a bridge network allowed through ufw to 9443:** needs a fixed
  bridge name and a new firewall exception for every Docker network change.
- **`docker compose up` from the pipeline:** works through the socket, but
  the stack is not managed by Portainer (no editor, limited control).
- **Image registry on MagicBox:** one more service; not needed with a single
  Docker host.
- **Apps on the Kong side discovered automatically (labels):** Kong DB-less
  has no Docker discovery; Ansible keeps the configuration reviewable.
- **App routes added by each pipeline through the Kong Admin API:** DB-less
  Kong replaces the whole configuration; it would drift from Ansible.

## Consequences

- A new app needs: an entry in `apps/registry.yml` and `make apps`, a
  Multibranch Pipeline in Jenkins, and `127.0.0.1:<port>` in its
  `deploy/stack.yml` matching the registry.
- The deploy step uses the Docker socket and the host network: as with
  ADR-0014, pipelines are trusted code (private repositories, no fork builds).
- Old images of an app are removed by its pipeline after a successful deploy;
  the Docker build cache grows and is not pruned automatically.
- Pushes are picked up by polling (5 minutes), not webhooks (ADR-0014).
