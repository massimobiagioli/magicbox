# ADR-0014: Jenkins on MagicBox for CI/CD, polling GitHub

- **Date:** 2026-10-29
- **Deciders:** MagicBox maintainers

## Status

Accepted

## Context

Applications live in GitHub repositories and run as Docker Compose stacks in
Portainer on MagicBox. The owner wants GitHub used only as a repository: no
GitHub Actions, neither cloud runners nor a self-hosted runner on MagicBox
(tried and rejected). CI/CD must run on MagicBox, as a Portainer stack, and
cover lint, tests, migrations, image build and deployment.

MagicBox is LAN-only (ADR-0004, ADR-0012): GitHub cannot reach it, so webhook
triggers are impossible and the CI server must poll GitHub. Woodpecker and
Drone start only from forge webhooks; Concourse polls but adds its own model
and heavier workers; Buildbot polls and is light but needs Python
configuration for everything. Jenkins polls natively (SCM polling, periodic
multibranch scans) and is the most established option.

## Decision

- Deploy Jenkins LTS (`jenkins/jenkins:2.580.2-lts-jdk21`) as the Portainer
  stack `jenkins` with `playbooks/ci-cd.yml` (`make ci-cd`), reusing the
  `stacks` role (create/update through the Portainer API, verification).
- Build two images on MagicBox; the tag is a hash of the build files:
  - controller: base image + plugins pinned in `stacks_jenkins_plugins`,
    installed by `jenkins-plugin-cli` at build time (no installs from the UI);
  - agent: `jenkins/ssh-agent` + Docker CLI + uv + git/make.
- Configure Jenkins only with Configuration as Code (JCasC), rendered by
  Ansible: local `admin` user, no sign-up, no anonymous access, 0 executors on
  the controller, one SSH agent `docker-agent` (label `docker`). Secrets
  (admin password, optional GitHub and Portainer tokens, agent SSH key) are
  files in `/run/secrets` with mode 0400, never environment variables or
  Portainer stack env.
- The UI is served over HTTPS on port 8443 with the MagicBox certificate
  (PKCS#12 copy) and reachable only from the LAN (DOCKER-USER). The agent is
  not published.
- The agent mounts the host Docker socket to build images and run test
  containers. This is equivalent to root on MagicBox, the same trust level as
  Portainer (ADR-0006). Mitigations: private repositories, no builds of pull
  requests from forks, migrations and deploys only from `main`, login required.

## Alternatives

- **GitHub Actions (cloud or self-hosted runner):** rejected by the owner.
- **Exposing Portainer/Jenkins webhooks through a tunnel:** breaks LAN-only.
- **Buildbot:** lighter, also polls; rejected for the smaller ecosystem and
  more configuration code. A reasonable fallback if Jenkins proves too heavy.
- **Concourse:** polls, but heavier and with a learning curve.
- **Woodpecker, Drone:** webhook-only triggers; incompatible with LAN-only.
- **Docker-in-Docker or rootless BuildKit for the agent:** better isolation,
  more moving parts; can replace the socket later without changing pipelines
  that only use `docker build`/`docker run`.

## Consequences

- One more stack: about 1 GB heap for the controller (memory limit 2 GB) and
  up to 4 GB for builds; builds compete with the other stacks for CPU/RAM.
- Plugin updates are deliberate: change `stacks_jenkins_plugins`, run
  `make ci-cd` (new image tag, redeploy), test. Plugin dependencies are
  resolved at build time, so two builds of the same tag can differ slightly.
- Jobs (multibranch pipelines) are created in the UI for now; their
  definitions live in each application's `Jenkinsfile`. JCasC-managed settings
  changed in the UI are overwritten at the next start.
- Pipelines on the agent talk to the host engine: bind mounts of the workspace
  (`docker run -v $PWD:...`) refer to host paths and do not work; use
  `docker build` contexts or named volumes instead.
