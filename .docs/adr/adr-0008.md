# ADR-0008: Explicit confirmation for destructive changes

- **Date:** 2026-10-28
- **Deciders:** MagicBox maintainers

## Status

Accepted

## Context

Some steps can cut off access or destroy state: enabling a firewall over SSH,
or removing distribution container packages (`docker.io`, `containerd`, `runc`,
`podman-docker`) that existing workloads may use. Running the playbook
casually must never do this by surprise.

## Decision

- A single boolean, `magicbox_confirm_destructive` (default `false`), gates
  destructive steps. It is passed per run with
  `-e magicbox_confirm_destructive=true` and never stored in inventory.
- Gated steps: first-time activation of ufw; removal of packages that conflict
  with Docker CE. Each refusal explains what would happen and how to proceed.
- Independent of the flag, ufw is never enabled when the controller connects
  from outside `magicbox_lan_cidr`.
- Data stores are never deleted by the playbook: the `portainer_data` volume,
  TLS material and the CA survive every run. Destroying them is a manual,
  documented recovery action.

## Alternatives

- **Per-step flags:** finer-grained but more to remember; rejected for now.
- **`pause` prompts:** break non-interactive runs and idempotency checks;
  rejected.

## Consequences

- The first deployment on a fresh host needs the flag once; later runs do not.
- New destructive steps must reuse this flag and be listed in this ADR and the
  playbook reference.
