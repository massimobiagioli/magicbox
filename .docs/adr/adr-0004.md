# ADR-0004: Host firewall with ufw and host networking for Portainer

- **Date:** 2026-10-28
- **Deciders:** MagicBox maintainers

## Status

Accepted

## Context

Management access (SSH, Portainer) must be limited to the intended LAN. Docker
inserts its own iptables rules for published container ports; those rules are
evaluated before ufw's INPUT chain, so a `-p 9443:9443` publish would ignore
ufw restrictions. Portainer mounts the Docker socket and is therefore already
root-equivalent (ADR-0006), so network-namespace isolation adds little security
for this particular container.

## Decision

- ufw is enabled with default deny inbound / allow outbound. Only these are
  allowed, and only from `magicbox_lan_cidr`: TCP 22 (SSH), TCP 9443
  (Portainer), UDP 5353 (mDNS).
- Portainer runs with `network_mode: host` and `--bind-https=:9443
  --http-disabled`, so its port is a normal host socket filtered by ufw. The
  plain-HTTP port 9000 is disabled.
- The Edge tunnel port 8000 is not used and stays blocked by the default-deny
  policy.
- The playbook refuses to enable ufw when the controller's SSH connection comes
  from outside `magicbox_lan_cidr`, and refuses first-time activation without
  confirmation (ADR-0008).

## Alternatives

- **Bridge network + `DOCKER-USER` rules in `/etc/ufw/after.rules`:** keeps
  network isolation but couples ufw and Docker rule ordering; more moving parts
  for no real gain while the Docker socket is mounted; rejected for now.
- **Bind the published port to the LAN IP only:** still bypasses ufw source
  filtering, and MagicBox's IP is dynamic (ADR-0003); rejected.
- **nftables directly:** more expressive but less familiar and less
  self-documenting than ufw; rejected.

## Consequences

- ufw is authoritative for Portainer.
- **Risk:** stacks deployed later through Portainer that publish ports on the
  default bridge bypass ufw. Bind such ports to `127.0.0.1`, or add a
  `DOCKER-USER` policy in a new ADR before exposing them.
- Changing the LAN subnet requires updating `magicbox_lan_cidr` and re-running
  the `firewall` tag from inside the new subnet.
