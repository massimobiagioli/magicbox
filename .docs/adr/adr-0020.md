# ADR-0020: Private Docker registry on MagicBox for app images

- **Date:** 2026-11-04
- **Deciders:** MagicBox maintainers

## Status

Accepted

## Context

App images are built by Jenkins on MagicBox and exist only in the local
Docker engine (`magicbox/<name>:<commit>`, ADR-0016). Apps should instead be
pushed to a registry, so that images are versioned in one place, can be
pulled by Portainer or by LAN machines, and survive a local image prune.
Docker Hub or GHCR would publish private images outside the LAN and add a
dependency on Internet access for every deployment.

Docker clients address a registry as `<host>:<port>/<image>` and require the
API at the root (`/v2/`), so it cannot live under a gateway path (ADR-0015).
Docker refuses plain HTTP for any registry other than `127.0.0.0/8` unless
it is listed as insecure in every client's `daemon.json`.

## Decision

- The registry is the Portainer stack `registry`, deployed by `make deploy`
  with the other stacks: CNCF Distribution (`registry:3`, pinned in
  `stacks_registry_image`), one data volume `registry_data`.
- HTTPS on `stacks_registry_port` (5000) with a copy of the MagicBox
  certificate; published and limited to the LAN by DOCKER-USER (ADR-0012).
  Images are named `magicbox.local:5000/<name>:<tag>`.
- Login required for push and pull: htpasswd (bcrypt) with user
  `stacks_registry_user` (`magicbox`) and `vault_registry_password`. The hash
  is made by `htpasswd` in a pinned `httpd` image and rewritten only when it
  no longer matches the vault password (idempotent despite the salt).
- The MagicBox Docker engine trusts the MagicBox CA for the registry
  (`/etc/docker/certs.d/magicbox.local:5000/ca.crt`, no daemon restart), so
  the Jenkins agent (host engine) can push without insecure settings.
- Jenkins gets the credential `registry` (username/password); the app
  template's pipeline pushes `magicbox.local:5000/<app>:<commit>` with a
  throwaway client login (stage Push).
- The registry is added to Portainer (custom registry with login), so stack
  deployments pull app images from it; the template's stack no longer uses
  `pull_policy: never`, and updates pull the image.
- Gateway: `https://magicbox.local/registry` is a 301 redirect to
  `https://magicbox.local:5000/v2/_catalog` (`stacks_kong_port_redirects`).
- Deletion through the API is enabled; disk space is reclaimed with the
  registry's own garbage collection, run by hand.

## Alternatives

- **Plain HTTP on 127.0.0.1 only:** no TLS or login needed for pushes from
  MagicBox, but LAN machines could not pull; rejected.
- **Plain HTTP on the LAN with `insecure-registries`:** credentials and layers
  in clear, and every client must change `daemon.json`; rejected.
- **Harbor:** UI, scanning and RBAC, but about ten containers and a database;
  too heavy for a single mini PC.
- **Gitea/Forgejo package registry or GHCR:** a second Git platform, or images
  outside the LAN; rejected.

## Consequences

- LAN clients must trust the MagicBox CA for `magicbox.local:5000` (on Linux
  `/etc/docker/certs.d/`, on Docker Desktop the system keychain) and log in
  with `docker login magicbox.local:5000`.
- Apps created from older template versions keep local-only images until
  their `Jenkinsfile` and `deploy/` are replaced with the template's.
- Deployments now depend on the registry being up; a stack update fails if
  the image is missing from it.
- After a certificate renewal, `make deploy` refreshes the registry's copy.
- No redundancy: back up `registry_data`, or rebuild images from Git.
