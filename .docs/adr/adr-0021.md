# ADR-0021: One idempotent `make deploy` for the whole infrastructure

- **Date:** 2026-11-04
- **Deciders:** MagicBox maintainers

## Status

Accepted (supersedes the separate stack playbooks of ADR-0011, ADR-0014,
ADR-0015, ADR-0017 and ADR-0018)

## Context

The infrastructure had grown to six playbooks and make targets that had to
run in a fixed order: `make deploy` (host, Portainer), `make stacks`,
`make ci-cd`, `make api-gateway`, `make storage`, `make apps`. Forgetting one,
or running them out of order, left MagicBox half configured (e.g. the gateway
without app routes, or certificate copies not refreshed after a renewal).
Every playbook was already idempotent and used the same `stacks` role.

## Decision

- `playbooks/site.yml` deploys everything, in order: host and Portainer
  roles, the controller check, the `stacks` role with every stack in
  `stacks_enabled` (default stacks, RustFS, registry, Jenkins, Kong), then the
  apps registry (`apps.json`, Jenkins jobs, report).
- `make deploy` is the only installation command; `stacks.yml`, `ci-cd.yml`,
  `api-gateway.yml`, `storage.yml`, `apps.yml` and their make targets are
  removed. Besides it, the Makefile keeps only `setup`, `check`, `manuals`,
  `test-container`, `status`, `update`, `vault-edit`.
- The first run still needs `-e magicbox_confirm_destructive=true`
  (ADR-0008); later runs are routine and must report `changed=0` on a
  converged host (`tools/idempotency_check.py`).
- Tags (`stacks`, `apps`, role tags) keep partial runs possible for
  debugging; `-e '{"stacks_enabled": [...]}'` limits the stacks.
- The container test runs the same playbook: host only by default,
  `--stacks all` for the whole deployment, `--stacks a,b` for a subset.

## Alternatives

- **Keep the playbooks and add an aggregate target:** the order lives in the
  Makefile and every playbook repeats the Portainer login; rejected.
- **A new `deploy.yml` importing the old playbooks:** keeps five entry points
  that nobody should run alone; rejected.

## Consequences

- One vault prompt and one run; a routine run takes longer (every stack is
  checked and verified), and all stack secrets are required up front.
- After adding an app (`tools/new_app.py`), changing the vault, or renewing
  the certificate, the next step is always `make deploy`.
- Removing a stack from `stacks_enabled` still does not delete it.
